# Customer Refund and Dispute Policy — Version 1.0

Status: engineering publication candidate. Rates, eligibility windows, and dispute-resolution timelines require Finance/Legal approval before taking effect. This document governs the customer-facing refund relationship; publisher-facing revenue/refund/support obligations are separately published in [publisher-revenue-refund-support-v1.0.md](./publisher-revenue-refund-support-v1.0.md).

A refund request is handled through the same commerce ledger as the original payment: an administrator-initiated refund or a provider-reported dispute both append a reversing entry rather than rewriting the original order, and both are idempotent — a duplicate refund request against an already-refunded order is rejected, not double-processed (`E-009`, live-verified: 22/22 checks including "admin refund + idempotent retry"). A refund or for-cause revocation stops future downloads and renewals of the affected product; it is a distinct action from a security emergency-disable, which follows its own signed advisory process regardless of any customer's payment status.

**A refund does not retroactively revoke an already-delivered offline entitlement token.** This is a deliberate design property, not an oversight: because entitlement verification is local and offline-tolerant ([ADR-0006](../architecture/adr/0006-licensing.md)), a token already issued to an installation keeps working for the functionality it already granted until that installation's normal refresh cycle picks up the revoked state, or until a distinct security advisory forces immediate action. A customer should be told this plainly at the point of refund request, not discover it afterward: **"a refund stops future updates and renewals; it does not retroactively disable functionality already downloaded and activated."**

**Eligibility windows and dispute-resolution timelines are not set by this document** — they require Finance/Legal sign-off, informed by DEC-002 (commercial model) and DEC-009 (payment provider order) once both are accepted. What this document does fix, because it is already an enforced technical invariant regardless of policy: money is always integer minor units plus ISO currency (never floating point), order totals are always computed server-side from versioned price records, and every refund/dispute event is permanently retained in the ledger — a correction is a new entry, never an edit to history.

A payment dispute opened with the provider (a chargeback) is treated as a forced reversal through the same ledger, distinct from an administrator-initiated refund, so that dispute outcomes (including a dispute resolved in the customer's favor without a formal refund request) are reflected consistently rather than requiring a second manual reconciliation step (`E-009`).
