# Publisher Plugin Lifecycle and Incident Procedures

## Vulnerable or malicious

Freeze publication, preserve package/review/build evidence, classify severity, and use the atomic withdrawal plus advisory procedure in [repository-security-incident.md](./repository-security-incident.md). Malicious behavior or active critical exploitation permits emergency disable. Never delete installed data or replace immutable bytes.

## Abandoned

Contact every verified publisher owner and support member. Mark the plugin unsupported, stop new sales, keep existing artifacts available only where security permits, publish end-of-support dates, and require a documented export/migration path. Transfer is not implied by abandonment.

## Ownership dispute or transfer

Suspend new releases and payouts while evidence is reviewed. A transfer requires current and proposed owners, legal/marketplace approval, verified new organization membership, new signing key enrollment with dual control, customer notice, and an audit record. Existing publisher signatures remain attributed to their historical publisher; database ownership fields are never silently rewritten.

## Tabletop acceptance

Run at least these scenarios before Gate F2: vulnerable release withdrawal/advisory; malicious submission rejection; abandoned paid plugin; ownership dispute during payout; publisher-key rotation; and a customer support case. Record participants, timestamps, decisions, communications, retained evidence, recovery, and gaps.
