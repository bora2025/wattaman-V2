# Secrets Inventory (A-008)

Every credential and private key across the two deployable backends (`backend`, `apps/marketplace-api`) and the plugin trust model, with generation, custody, rotation, expiry, revocation, and redaction status. Distinguishes true secrets (need confidentiality) from public/integrity-sensitive material (needs tamper-resistance, not secrecy) — several entries below are the latter and were previously listed alongside real secrets in `technical-inventory.md`'s configuration table without that distinction.

## School API (`backend`)

| Secret | Generation | Custody today | Rotation | Expiry | Revocation | Redaction |
|---|---|---|---|---|---|---|
| `JWT_SECRET` | Operator-generated (no in-repo generator); must be ≥32 chars and not the known development placeholder — enforced at startup (`config/environment.ts`, `FND-002`) | Deployment environment variable (Railway/Compose secret) | [Runbook](./secret-rotation-runbooks.md) — no grace overlap; rotating invalidates every issued access/refresh token instantly. Documented as a scheduled-maintenance-window operation, not silently undocumented anymore | None — a JWT_SECRET has no built-in expiry; only token *lifetimes* (`JWT_ACCESS_EXPIRY`/`JWT_REFRESH_EXPIRY`) expire | Same as rotation — there is no way to revoke this secret without also invalidating every active session | Never logged; not present in any status/diagnostic endpoint |
| `DATABASE_URL` | Provisioned by the hosting platform (Railway) or operator (Compose) | Deployment environment variable | [Runbook](./secret-rotation-runbooks.md) — changing the DB password requires coordinated update of this var and the database itself | None | Revoking means changing the DB user's password, which requires downtime coordination — not automated | Never logged; Prisma error messages have historically leaked query text but not credentials |
| `RefreshToken.token` (database column) | Generated per login by `auth.service.ts` | **Stored in plaintext in the database** — a known, pre-existing gap (see `implementation-baseline.md`'s E-001 comparison note: "RefreshToken's plaintext-storage/no-reuse-detection gap"). Anyone with read access to the `RefreshToken` table can impersonate any session without cracking anything | Expires and is replaced on refresh (`JWT_REFRESH_EXPIRY`) | Bounded by `JWT_REFRESH_EXPIRY` | Deleting the row revokes it; no reuse-detection (a stolen-and-reused old token isn't flagged) | The column itself is the exposure — token values could appear in a DB dump or backup without any additional redaction layer |
| `PLUGIN_TRUSTED_KEYS` / `PLUGIN_TRUSTED_KEYS_FILE` | Generated by `wattanam-plugin keygen` (Ed25519 keypair) — **only the public key half is configured here** | This variable holds public keys; it is integrity-sensitive, not confidential — tampering (adding an untrusted key) is the real risk, not disclosure | Add the new public key alongside the old one during a rotation window, remove the old one once no installed plugin needs it | None inherent | Remove the entry; any plugin signed by that key fails verification on next load | Not a secret — safe to log/display, but must be tamper-evident (delivered via a trusted deploy pipeline, not user input) |
| `PLUGIN_MAX_PACKAGE_BYTES`, `PLUGIN_MAX_UNPACKED_BYTES`, etc. | N/A — not secrets | — | — | — | — | Listed in `technical-inventory.md` for completeness; not a secrets-inventory concern |
| Plugin signing **private** keys (generated by `wattanam-plugin keygen`, e.g. for the `wattanam` publisher) | `packages/plugin-cli`'s `keygen` command (Ed25519) | **Must never be committed or stored on any server** — lives only with whoever signs releases. This repo has no automated custody; it's an operational discipline requirement today | No procedure defined; would require re-signing every future release with the new key and distributing the new public key via `PLUGIN_TRUSTED_KEYS` | None inherent | Remove the corresponding public key from `PLUGIN_TRUSTED_KEYS` everywhere it's deployed | The private key file itself is the secret; `*.pem`/`*.key` are `.gitignore`d at the repo root |
| `SENDGRID_API_KEY` | Provisioned by SendGrid | Deployment environment variable | [Runbook](./secret-rotation-runbooks.md) | Provider-side (SendGrid dashboard) | Revoke in the SendGrid dashboard; app fails closed (`config.email.enabled` false) without it | Never logged; `notification-config.ts` validates shape without echoing the value |
| `TWILIO_ACCOUNT_SID` / `TWILIO_AUTH_TOKEN` | Provisioned by Twilio | Deployment environment variable | [Runbook](./secret-rotation-runbooks.md) | Provider-side | Revoke/regenerate in the Twilio console | Never logged |
| `METRICS_TOKEN` | Operator-generated, ≥32 chars (`observability/metrics-config.ts`) | Deployment environment variable, read independently of `readRuntimeConfig()` (a scraper can't do interactive JWT login, so it gets its own credential rather than reusing anything else) | [Runbook](./secret-rotation-runbooks.md) — no overlap window, but the lowest-stakes secret to rotate in this inventory (worst case is one missed Prometheus scrape) | None | Change the env var and the Prometheus scrape config's `bearer_token` together; redeploy | Never logged; only ever compared via `timingSafeEqual` against the `Authorization` header |

## Marketplace API (`apps/marketplace-api`)

| Secret | Generation | Custody today | Rotation | Expiry | Revocation | Redaction |
|---|---|---|---|---|---|---|
| `MARKETPLACE_ADMIN_TOKEN` | Operator-generated, ≥32 chars, checked with a constant-time comparison (`app.ts`'s `adminGuard`) | Deployment environment variable | [Runbook](./secret-rotation-runbooks.md) — a single shared token for every admin action (`POST /admin/v1/*`); update every caller before redeploying with the new value, since there is no dual-token grace period | None | Change the env var and redeploy; all prior holders lose access immediately (no graceful handoff) | Never logged; used only in the `authorization: Bearer` header, never echoed |
| `DATABASE_URL` (marketplace) | Provisioned by the hosting platform (Railway) or operator (Compose) — a separate database and credential from the school API's `DATABASE_URL`, never shared | Deployment environment variable | [Runbook](./secret-rotation-runbooks.md), same gap and same procedure shape as the school API's `DATABASE_URL` | None | Requires coordinated DB user password change and downtime, same as the school API | Never logged |
| `IDENTITY_ENCRYPTION_KEYS_JSON` / `IDENTITY_ENCRYPTION_ACTIVE_KEY_ID` | Operator-generated 32-byte keys (`secret-encryption.ts`), required in production once any identity data needs encrypting | Deployment environment variable; protects `MarketplaceAccount.mfaSecret` at rest (AES-256-GCM) | **Self-healing, live-verified end to end** ([runbook](./secret-rotation-runbooks.md)) — a multi-key ring plus an active-key pointer means an old key stays valid for decryption while new writes use the new one, and `identity.service.ts` transparently re-encrypts a row under the active key the next time its owner completes a TOTP login. No bulk migration script needed to complete a rotation, only to accelerate it | None inherent | Remove the old key from the ring once no row still decrypts under it | Never logged; the encrypted envelope (`enc:v1:<keyId>:...`) is safe to appear in a DB dump — the key itself, not the ciphertext, is the secret |
| `METRICS_TOKEN` (marketplace) | Same shape as the school API's | Deployment environment variable, independent of `readConfig()` | [Runbook](./secret-rotation-runbooks.md) | None | Change the env var and the Prometheus scrape config together; redeploy | Never logged |
| `METADATA_SIGNING_PRIVATE_KEY(_FILE)` | Generated externally (same `wattanam-plugin keygen`-style Ed25519 flow, or the marketplace's own key-generation path) | Deployment secret file/variable | **Multi-key rotation exists** (`METADATA_SECONDARY_SIGNING_KEYS_JSON`/`_BASE64`) — a new key can be added alongside the active one so old clients pinned to the old key keep verifying during an overlap window (`gate-d-official-repository` evidence covers a live `repository-2026`/`repository-2027` drill) | None inherent | Remove from the secondary-keys set once every client has migrated to the new primary key | Never logged; `readPrivateKey` reads from file or env, never returns the raw value in any response |
| `ENTITLEMENT_SIGNING_PRIVATE_KEY(_FILE)` | Same as above | Deployment secret | [Runbook](./secret-rotation-runbooks.md) — a written procedure now exists (add the new key to every school's `ENTITLEMENT_SECONDARY_PUBLIC_KEYS_JSON` first, then swap the issuing key, then remove the old trusted key once no unexpired entitlement depends on it), but unlike the repository key it has not been live-drilled yet — stated as a real remaining gap, not implied done | None inherent | Same as repository key | Never logged |
| `PAYMENT_WEBHOOK_SECRET` | Operator-generated, ≥32 chars | Deployment environment variable | [Runbook](./secret-rotation-runbooks.md) — rotating breaks in-flight webhook verification from the payment provider until both sides update simultaneously | None | Change and redeploy; provider must be updated at the same time or webhooks start failing signature checks | Never logged |
| `PublisherKey.publicKeyPem` (database column) | Publisher-generated, submitted at registration | **Public key data — not a secret.** The corresponding private key never touches this server | A publisher submits a new key; the old one is marked `revokedAt` (see `docs/marketplace/official-repository.md`) rather than deleted, preserving verification of already-published historical artifacts | None inherent (a specific key can be revoked, doesn't expire on its own) | `revokedAt` timestamp set — `repository.service.ts` excludes revoked keys from the trusted-publisher lookup | Not a secret; safe to expose via `GET /v1/repository-key` by design |
| `UPDATE_REPOSITORY_PUBLIC_KEY(_FILE)` (school-side, in `backend`) | Mirrors the marketplace's repository signing public key | Deployment config on the school side | Update alongside a repository key rotation, via `UPDATE_REPOSITORY_PUBLIC_KEYS_JSON` for multi-key overlap | None inherent | Remove from the trusted set | Not a secret |

## What's missing (the real gap A-008 asks about)

- ~~No rotation drills exist for most secrets.~~ **Addressed 2026-08-29** —
  [secret-rotation-runbooks.md](./secret-rotation-runbooks.md) gives every secret in both
  tables above a concrete procedure. Real, honest distinctions remain within that document:
  the repository signing key and the new `IDENTITY_ENCRYPTION_KEYS_JSON` mechanism are
  *live-drilled* (the identity-encryption rotation end to end, in this pass, against a real
  disposable PostgreSQL 16); the entitlement signing key has a *written* procedure using an
  already-existing multi-key verification mechanism but has never been drilled; `JWT_SECRET`,
  `MARKETPLACE_ADMIN_TOKEN`, `PAYMENT_WEBHOOK_SECRET`, `METRICS_TOKEN`, and both `DATABASE_URL`s
  have no graceful overlap at all — their "procedure" is an explicit maintenance-window
  cutover with the real impact stated, not a technical gap a runbook alone can close.
- **No centralized secret-generation tooling** beyond `wattanam-plugin keygen` (Ed25519 keypairs only) — every other secret in both tables above is "operator generates it somehow" with no documented, repeatable procedure or minimum-entropy tooling.
- **`RefreshToken.token` plaintext storage** is the one *currently-live* secret-handling gap identified here that isn't just "no rotation procedure" — it's an at-rest exposure. Fixing it (hash at rest, add reuse-detection, matching the pattern already built for the marketplace's own session tokens in E-001) is real engineering work, not a documentation gap, and is out of scope for this inventory itself.
- ~~No secret-scanning in CI.~~ **Addressed 2026-08-29** — `.github/workflows/pr-validation.yml` runs `gitleaks` against every pull request (see [gate-cicd-pr-validation-2026-08-29.md](../acceptance/gate-cicd-pr-validation-2026-08-29.md)), with a `gitleaks.toml` allowlist for the two confirmed false positives found in this repo's own history.

## Change rule

Every new secret-shaped environment variable or database column must be added to this inventory in the same change, with its generation/custody/rotation/expiry/revocation/redaction answered honestly — "no procedure exists" is an acceptable, better-than-nothing answer; a missing row is not.
