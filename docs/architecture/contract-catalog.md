# Public Contract Catalog (A-010)

Status: generated by direct code audit, 2026-08-29 (`backend/src`, `apps/marketplace-api/src`, `apps/mobile`, `frontend/app/api`, `packages/plugin-sdk`). Every route below is cited by file:line at the time of the audit; a line number may drift as the code changes, but the *route* is the contract this catalog tracks — re-run the audit when a controller/gateway file changes, per the change rule at the bottom.

This catalog covers the five contract surfaces [technical-inventory.md](./technical-inventory.md) named as A-010's scope: **School REST and Socket.IO**, **plugin package/runtime**, **marketplace repository envelopes**, **the browser server proxy**, and **the mobile consumer**.

## 0. How to read this

- **No global versioning exists on the school API.** There is no URL prefix, no header-based version negotiation, and no `enableVersioning()` call anywhere in `backend/src/main.ts`. The only version-related endpoint is `GET /version`, which *reports* `APP_VERSION` — it does not gate routing. Contrast: `apps/marketplace-api` uses an explicit `/v1/*` and `/admin/v1/*` URL prefix; the plugin SDK versions via semver ranges (`requiresCore`, `sdkVersion`, `runtimeVersion`) checked at parse/activation time. §5 below covers the compatibility/deprecation policy this asymmetry implies.
- **Auth column values**: `public` (no guard at all), `JWT` (any authenticated user, `JwtAuthGuard`), `JWT+Roles: X,Y` (`JwtAuthGuard`+`RolesGuard`, restricted to the named roles), `admin token` (marketplace `MARKETPLACE_ADMIN_TOKEN`), `session` (marketplace customer session), `installation signature` (marketplace, school-installation-signed request).
- A route with **no `@Roles()`** but a `JwtAuthGuard` is reachable by *any* authenticated role — this is intentional in several places (e.g. `PluginApiController`'s dispatcher, which pushes real authorization down to the plugin's own declared permission grant) and is called out explicitly where it appears.

### Attendance (`/attendance`) — 19 routes
Record/bulk/check-out/create/update/delete for both student and staff attendance, an employee self-scan path, a role-restricted `WATTAMAN` class-free scan role, and read endpoints for records/daily totals. Roles used: `TEACHER,ADMIN,CLASS_ADMIN` (student-side mutations), `ADMIN`/`ADMIN,WATTAMAN_REPORTER` (staff-side + edits), plain `JWT` (self-service reads/scans). Full route list: `record`, `bulk`, `check-out`, `staff/record`, `staff/check-out`, `staff/auto-scan`, `employee/self-scan`, `employee/my-records` (GET), `records` (GET), `staff/records` (GET), `update` (PATCH), `edit-permission-type` (PATCH), `staff/update` (PATCH), `create-record`, `staff/create-record`, `staff/edit-permission-type` (PATCH), `record` (DELETE), `staff/record` (DELETE), `user-daily` (GET), `wattaman/scan`.

### Bus (`/bus`) — class guard JWT+Roles

CRUD for buses/routes/stops (`ADMIN`), plus location read/write shared with `TEACHER,PARENT,STUDENT` for reads and `ADMIN,WATTAMAN` for location writes. `POST /bus/:id/location` also broadcasts over `BusGateway` (§2).

### Card aliases / templates (`/card-aliases`, `/card-templates`)

Physical-card-to-student resolution (`ADMIN,WATTAMAN`) and card visual-design CRUD (`ADMIN`, with one shared-read route `GET /card-templates/active/:cardType` open to any authenticated role).

### Departments, Holidays, Study Years, Session Config

Straightforward CRUD, reads open to any authenticated user, writes restricted to `ADMIN`. Session Config additionally exposes `format-rules` (attendance grace/lateness rules) and `staff-schedule`.

### Notification preference (`/notification-preference`), Messages (`/messages`), Parent (`/parent`)

Own-preferences read/update (any authenticated role); parent-teacher direct messaging (`PARENT,TEACHER,ADMIN,STUDENT`); parent-child linking self-service request + admin approval queue.

### Reports (`/reports`) — 25 routes

Dashboards, trends, CSV/XLSX exports (student and staff), duplicate-student detection, and self-service "my" variants for employees. Mixed `ADMIN`/`ADMIN,WATTAMAN_REPORTER`/plain-`JWT` (self-service) access.

### Salary, Scoring, Fees (`/salary`, `/scoring`, `/fees`)

Salary: full CRUD, `ADMIN` only. Scoring: score-sheet/subject/exam-tab/entry management, `ADMIN,TEACHER,CLASS_ADMIN`. Fees: student fee records, payments, and school-level fee settings, `ADMIN,ACCOUNTER` (mutations to existing records tighten to `ADMIN` only for update/delete).

### Timetable (`/timetable`) — 27 routes

Full timetable generation and CRUD across subjects/classes/classrooms/teachers/lessons/entries (`ADMIN`), plus teacher-attendance scanning (one route, `/timetable/teacher-attendance/scan`, has **no `@Roles()` restriction at all** — any authenticated user can call it — while its `wattaman-scan` sibling is `ADMIN,WATTAMAN`).

### Site settings (`/site-settings`) — **no class-level guard**

`GET /site-settings` is explicitly public (code comment: "all portals and the homepage can read... without auth"); `PATCH` is `ADMIN`.

### Posts (`/posts`) — mixed public/admin

`GET /posts/published` and `GET /posts/:id` are public (homepage feed); `GET /posts` (unfiltered) and all mutations are `ADMIN`.

### Courses (`/courses`) — 37 routes, the largest single controller

Full LMS: course CRUD/status transitions, enrollments, lessons/pages, student attempts/responses/grading, sessions/attendance/check-in, lesson-view engagement tracking, and an engagement report. `ADMIN,SUPER_ADMIN,TEACHER` for authoring/grading; `+STUDENT` added on read/attempt/check-in routes.

### Assignments, Exam (`/assignments`, `/exams`)

Assignment/question/submission CRUD and grading (`ADMIN,TEACHER`), student-facing quiz-taking and submission (`STUDENT,ADMIN`). Exam mirrors this shape with a student-safe "take" view that strips answer keys (`GET /exams/:id/take`).

### Staff CV, Classes, Class Registrations

Staff CV read/update (`ADMIN`). Classes: full CRUD plus CSV bulk-import (`ADMIN,CLASS_ADMIN`), several reads open to any authenticated role. **Class Registrations has no class-level guard**: `GET /class-registrations/public/classes`, `GET /class-registrations/public/form-config`, and `POST /class-registrations/public` (throttled 5/60s) are the **only unauthenticated, unauthenticated-submission intake surface in the entire backend** — matching [data-classification.md](./data-classification.md)'s flag that `ClassRegistration.photo` is "submitted pre-approval by an unauthenticated intake form — highest-exposure surface of any model in this schema."

### Installation (`/installation`) — **no guard at all** (pre-auth bootstrap, by design)

`GET /installation/status`, `POST /installation/install` (throttled 3/hour). This is the only controller with zero authentication anywhere, because it exists specifically to create the first owner before any credential exists — see [ADR-0002](./adr/0002-tenancy.md) and `INS-001`–`003`.

- `/audit` — logs/facets/export/stats/portal-activity/cleanup-schedules, `ADMIN,SUPER_ADMIN`.
- `/plugins` — install/inspect/activate/deactivate/permission-grants, `SUPER_ADMIN` only ([ADR-0004](./adr/0004-plugin-trust.md)).
- `/plugin-api` — `GET /plugin-api/extensions` (`SUPER_ADMIN`, unfiltered admin view), `GET /plugin-api/my-extensions` (any authenticated role, filtered), `ALL /plugin-api/:pluginId/*` (any authenticated role reaches the dispatcher; real authorization is per-route inside `PluginExtensionsService.dispatch()` against the plugin's declared permission grants — see §3).
- `/announcements` — thin proxy into the `wattanam.announcements` plugin via the same dispatcher, preserving legacy URLs (`all`, `feed`, `unread-count`, `read`, create, remove).
- `/updates` — check/install/prepare/complete/maintenance/emergency-advisory, `SUPER_ADMIN`.
- `/admin/marketplace` — installation registration/key-rotation/entitlement refresh/export/import, `SUPER_ADMIN`.

## 2. Socket.IO / WebSocket events

All three gateways authenticate on connect via the shared `authenticateSocket()` helper (`backend/src/common/socket-auth.ts`) — the same JWT as REST, presented over the socket handshake; a failed check disconnects the socket. **Mobile does not use Socket.IO at all** (no `socket.io-client` dependency anywhere under `apps/mobile`) — all three gateways are web-only today.

| Gateway | Namespace | Client→server events | Server→client events |
|---|---|---|---|
| `AttendanceGateway` | `/` (default) | `joinClass`/`leaveClass` (room `class-${classId}`), `joinDashboard`/`leaveDashboard` (room `dashboard`) | `attendanceUpdate` (room `class-${classId}`), `dashboardUpdate` (room `dashboard`, `{classId, studentId, status, timestamp}`) |
| `BusGateway` | `/bus` | `subscribe-to-bus` (`{busId}` → joins `bus:${busId}`, acked), `location-update` (`{busId, latitude, longitude, speed?, heading?}`, requires `SUPER_ADMIN/SCHOOL_ADMIN/ADMIN/WATTAMAN`, acked) | `bus-location` (room `bus:${busId}`, `{busId, latitude, longitude, speed, heading, timestamp}`) |
| `MessagesGateway` | `/` (default) | `joinUser`/`leaveUser` (`userId`, must equal caller's own id, room `user-${userId}`), `typing` (`{from, to, isTyping}` → emits to `user-${to}`) | `message:new`/`message:sent` (room `user-${receiverId}`/`user-${senderId}`), `message:read` (room `user-${senderId}`, `{by}`) |

**Plugin-facing realtime** piggybacks on `MessagesGateway`'s server instance: `plugin-realtime.service.ts` emits `plugin:<pluginId>:<event>` to the same `user-${userId}` rooms, backing the `realtime.notifyUser()` capability (§3).

## 3. Plugin-facing contract (`api.routes`, `PluginRuntimeContext`)

Defined identically (by convention, not import — `packages/plugin-sdk` has no backend dependency) in `backend/src/plugins/plugin-sdk.ts` and `packages/plugin-sdk/src/types.ts`, pinned by two independent unit tests (`plugin-sdk-contract.spec.ts`, `manifest.spec.ts`) that must be kept in sync by review convention.

```ts
interface PluginRuntimeContext {
  sdkVersion: '1.0.0'; pluginId: string; logger: Logger;
  events: { publish(event, payload): void; subscribe(event, handler): () => void };
  routes: { register(definition: PluginRouteDefinition): () => void };
  jobs: { register(definition): Promise<() => void> };
  settings: { get<T>(key, fallback?): Promise<T|undefined>; set(key, value): Promise<void>; delete(key): Promise<void> };
  storage: { readText(name): Promise<string|null>; writeText(name, value): Promise<void>; delete(name): Promise<void>; list(prefix?): Promise<string[]> };
  permissions: { register(defs): () => void };
  navigation: { register(entries): () => void };
  notifications: { sendEmail(...); sendSms(...); notifyInApp(...) };
  database: { query<T>(sql, params?): Promise<T[]>; execute(sql, params?): Promise<{count}> };
  directory: { resolveAudience(...); lookupUsers(ids); lookupClasses(ids); classesForUser(userId, role) };
  realtime: { notifyUser(userId, event, payload): void };
}

interface PluginRouteRequest {
  method: 'GET'|'POST'|'PUT'|'PATCH'|'DELETE'; path: string;
  params: Record<string, string>; query: Record<string, string | string[]>;
  body: unknown; principal: { userId: string; role: string; email?: string };
}
```

**Registration/dispatch pipeline**: a plugin calls `context.routes.register({method, path, permission, handler})` → `PluginExtensionsService.registerRoute()` validates method/path shape, that `permission` is declared in the plugin's own manifest, and that `pluginId:METHOD:path` isn't already taken → two controllers translate real HTTP requests into `PluginRouteRequest` and call `PluginExtensionsService.dispatch()` (the generic `ALL /plugin-api/:pluginId/*` dispatcher, and the hardcoded `/announcements` legacy-URL proxy) → `dispatch()` checks the caller's role against the route's declared permission grant (403 + audit log if not granted), then races the handler against a 10s timeout, auditing success/failure either way.

**Compatibility gating**: a plugin may declare `sdkVersion`/`runtimeVersion` semver ranges (checked against the frozen `PLUGIN_SDK_VERSION`/`PLUGIN_RUNTIME_VERSION` constants) and **must** declare `requiresCore` (a semver range checked against the running `APP_VERSION`) — re-evaluated on every install *and* every activation/load, not just once at install time. This is the working three-layer pattern §5 generalizes for the rest of this catalog.

## 4. Marketplace API (`apps/marketplace-api/src`) — plain Express, explicit `/v1`/`/admin/v1` prefix

Separate service, separate database, separate deploy from `backend` ([ADR-0002](./adr/0002-tenancy.md)). Four auth tiers: **public**, **admin token** (`MARKETPLACE_ADMIN_TOKEN`, constant-time compare), **session** (customer bearer session token), **installation signature** (query-param `installationId, ts, signature`, no bearer token — verified against the installation's own registered key).

### Public / customer-session surface (`/v1/*`)

Repository key, publisher policies, signed release index, plugin catalog, artifact download (public for free plugins, session-or-installation-signature for paid), payment webhook (HMAC-verified), account registration/email-verification/sessions/password-reset, customer orders/entitlements, MFA enrollment, publisher self-registration + policy acceptance + key request + submission, installation registration challenge/register/key-rotation, installation-signed entitlement reads.

### Admin surface (`/admin/v1/*`) — every route admin-token-gated

Publisher/policy/member/reviewer management and approval, submission review, revenue recording (order settlement, refunds, corrections), publisher statements and payouts (create/approve/mark-paid), pilot metrics/launch-assessment, plugin/core release publish/promote/withdraw, order admin actions (manual settlement, refund), entitlement revoke/expire-overdue.

**By design, the entire `/admin/v1/*` surface and publisher-management routes have zero web/mobile consumers** — `frontend/app/api/marketplace/[...path]/route.ts` allowlists only the public/customer-session subset (catalog, publisher-policies, customer orders/entitlements, account/session/MFA/password-reset, signature-verified downloads) and never forwards an admin-token request from the browser.

## 5. The browser server proxies

- **`frontend/app/api/[...path]/route.ts`** (school API): a byte-for-byte transparent proxy. No allowlisting, no auth transformation — it forwards every header (including cookies/`Authorization`) and every method verbatim to `backend`. This means **every route in §1 is reachable from the browser** at the mirrored `/api/<path>`; all actual auth logic lives in `AuthController`, not in this proxy.
- **`frontend/app/api/marketplace/[...path]/route.ts`** (marketplace API): the opposite shape — an explicit allowlist of `GET`/`POST` paths, same-origin enforcement on POSTs, a `wattanam_marketplace_session` cookie required for session-scoped paths, and the marketplace's raw session token converted into an HttpOnly cookie rather than exposed to browser JS. This is the correct pattern for any future admin-adjacent surface that should reach the browser — §4's admin routes deliberately do not use it.

## 7. Breaking-change policy and the compatibility fixture

**Policy (proposed, not yet enforced by any versioning machinery on the REST/WebSocket surface — see §0):**

1. **Additive is always safe within the same `APP_VERSION` major**: a new route, a new optional field on a request, a new field on a response. No client should ever break from an addition.
2. **A path/method rename or removal, a required-field addition to a request, or a field removal/type change on a response is breaking** and requires a documented deprecation window: the old route keeps working for at least one full mobile-release cycle (matching [support-matrix.md](./support-matrix.md)'s proposed mobile window) after the new one ships, with the deprecated route logging a warning server-side.
3. **The plugin SDK's existing policy is the model to imitate once REST versioning exists**: additive-within-1.x is free, breaking requires a major bump with an overlap window ([package-and-runtime.md](./plugins/package-and-runtime.md)). Building actual URL/header versioning for the REST surface to enforce this mechanically is follow-on engineering this catalog identifies as needed, not work this catalog performs.
4. **Until that machinery exists, the compatibility fixture below is the enforcement mechanism**: it fails CI the moment a route a real client depends on stops resolving, which is the most common breaking-change shape in practice (see the plugin system's own `requiresCore` semver-range pattern, `plugin-package.spec.ts`, for the equivalent proven pattern on that surface).

**The fixture**: [`backend/test/mobile-compatibility.e2e-spec.ts`](../../backend/test/mobile-compatibility.e2e-spec.ts) covers installation discovery and every backend route the mobile client consumes. It asserts that routes remain present and every response advertises compatibility contract v1. Run it against a running, seeded backend with `npm run test:e2e`.

## Change rule

Same discipline as `technical-inventory.md`: a new controller, gateway event, marketplace route, or plugin-context capability is added to this catalog in the same change that adds it. A route consumed by `apps/mobile` gets added to `MOBILE_ROUTES` in the compatibility fixture in the same change, not retrofitted later.
